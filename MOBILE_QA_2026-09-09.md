# Mobile camera and output audit

## Product rules

- The live viewfinder is square. Its centered raw crop is a comparison aid, not part of the artwork.
- A tap captures a photo. A hold records up to five seconds; release or backgrounding finishes recording.
- Photos remain editable through presets, NICE TRY and reverse. NICE TRY changes both preset and palette.
- Recorded video is a finished effect result: review, confirm, share or retake. No raw crop, countdown or controls belong in the encoded file.
- The bottom dock owns its own layout space. Short viewports may scroll the controls, but the dock must never cover them.
- OUTPUT should invoke native sharing without an extra application-level SAVE screen whenever the browser supports it.
- Browser sharing is not proof of saving to Photos. The user still chooses the system action; a website cannot silently write to the iOS photo library.

## Defects corrected

1. The raw comparison crop was composited onto the same canvas captured by MediaRecorder. It now exists only on the display canvas. The encoder reads the clean effect canvas.
2. Controls used fixed-width columns and extended behind an absolutely positioned dock. Grid columns now fit the container; the controls end above the dock. Camera control heights adapt to available height, with independent overflow for very short viewports.
3. The progress frame and countdown were positioned with offsets from the shutter. They are now centered on the viewfinder using the same ratio as the raw crop.
4. OUTPUT always inserted another SAVE page. Sharing is now attempted directly. A debounced image export cache preserves the tap's transient activation; recipe/source changes invalidate the cache. Unsupported or failed sharing retains a recoverable preview.
5. Recording support failure disabled photography too. Unsupported recording now leaves preview and tap-to-photo usable.
6. Late camera permission/initialization responses could reactivate a closed camera page. Session checks discard and stop obsolete streams; metadata loading has a bounded wait.
7. A confirmed video could not return to the camera from the dock. The camera action now starts a new capture.
8. Backgrounding now cancels pending holds, finishes active recordings and pauses the preview loop. Visible previews resume the loop.

## Verification performed

Browser tests use `tools/mobile-regression.cjs`, a loopback-only fixture server. It injects a synthetic camera and a stub share target only into `/tools/mobile-qa.html`. The production HTML does not load this harness.

Actual browser canvas, MediaRecorder encoding and video decoding are exercised. A magenta camera marker must be present in the live comparison crop and absent from the decoded recording's center pixel.

Passed scenarios:

- PNG upload, prepared export, cache invalidation after NICE TRY, direct image share invocation.
- Tap photo and camera-track cleanup.
- Photo capture when MediaRecorder is unavailable.
- Hold/release recording, decoded square video without raw crop, review, confirmation and direct video share invocation.
- Five-second automatic stop.
- Front/back camera switching, old-track cleanup, random preset/palette, reverse and retake after confirmation.
- Background interruption of an active recording.
- Permission denial with recoverable error state.
- Permission request completing after camera exit, without reopening or leaking tracks.
- Unsupported sharing with fallback preview; cancelled sharing without an extra SAVE screen.
- Layout screenshots at 375x812, 390x844 and 430x932.
- Short viewport checks at 375x620 and 390x654; recording layout with a simulated 34px bottom safe area.
- Desktop 1440x900 entry-page screenshot and console check.
- Existing `tools/check-release.cjs`: syntax, 12 recipe/quality roundtrips, compatibility, dimensions and assets.

No application errors were reported by the completed browser fixtures. A browser-automation selector wait occasionally timed out even after the DOM result existed; the final DOM assertions were read and verified separately.

## Limits and remaining device checks

These are Chromium browser tests with simulated inputs, not a claim of physical iPhone Safari testing. Camera authorization prompts, hardware frame rate, iOS toolbar animation, and the actual Photos share-sheet action still require a real iPhone over HTTPS. A successful Web Share promise does not reveal which destination the user selected.

Already-saved videos containing the old raw crop cannot be repaired by this UI change; new captures use the corrected clean canvas.

The main HTML still contains several generations of mobile CSS overrides. This patch changes the affected ownership and geometry without a broad desktop refactor. A separate mobile stylesheet/state module would reduce future regression risk, but is not necessary for this focused correction.

## Reproduce

Run `node tools/mobile-regression.cjs`, open `http://localhost:4175/tools/mobile-qa.html?case=full` in a mobile-sized browser, and read `document.documentElement.dataset.qa` after completion.

Other cases: `preview`, `recording`, `limit`, `photo`, `photo-only`, `upload`, `lifecycle`, `background`, `cancel-request`, `denied`, `unsupported-share`, `cancel-share`. Add `&safe=34` to simulate the bottom inset in the fixture only.

The synthetic share target never saves a personal file or accesses a real camera.
